# Collaboration features (a familiar business-mail feature set)

Date: 2026-10-21 · Status: design accepted (ADR-0013); build phases in `09-roadmap.md`.

AnhourMail aims for the **mail collaboration** feature set people know from mainstream business mail suites,
sized for families and small groups: shared mailboxes, distribution lists, groups, delegated access (full access,
send as, send on behalf, folder sharing), resource mailboxes, mail flow rules, forwarding and auto-replies, and
message trace. This doc maps each feature to the pinned Stalwart Community edition (v0.16.27), says what our
control plane owns, and places it by plan and phase.

Evidence comes from three places: the server's JSON schema (`GET /api/schema`), **live probes against the dev
Stalwart** on 2026-10-21 (throwaway `collab-probe.test` / `collab-probe2.test` domains, all objects destroyed
afterwards), and the Stalwart docs ([Group](https://stalw.art/docs/auth/principals/group/),
[Sharing](https://stalw.art/docs/collaboration/sharing/)) plus support threads where the docs are thin
([mailing lists vs groups](https://support.stalw.art/t/use-mailing-lists-instead-of-groups-with-external-directories/1692),
[personal mailbox sharing via ACL](https://support.stalw.art/t/personal-mailbox-sharing-via-acl/1499),
[JMAP sharing gaps](https://support.stalw.art/t/jmap-sharing-is-incomplete-and-fails-real-world-use-cases/1555),
[read-only calendar share bug](https://support.stalw.art/t/read-only-calendar-share-grants-access-to-the-sharers-mailbox/1890)).
Forum posts are community reports, not vendor statements; they are marked as such below.

### Security findings from the probe (must fix before Phase 3)

1. **Header `From:` spoofing between local users.** An authenticated user sent a message with `From: shared@…`
   (a group they are **not** a member of) using their own identity; it was delivered internally. Stalwart's
   `MtaStageAuth.mustMatchSender` is already `true`, but it checks the SMTP envelope sender, not the header.
   Fix: (a) the BFF only submits with an identity the actor is allowed (control-plane check, audited), and
   (b) a system Sieve / data-stage rule that rejects authenticated submissions whose header `From` isn't one of
   the account's addresses. Never disable DMARC/alignment checks to make delegation work (rule 20).
   **Closed in Phase 1 (2026-10-21, ADR-0019):** the `sender-identity` Sieve system script runs at DATA for
   authenticated sessions and requires exactly one header From equal to the (already validated) envelope sender,
   and a matching `Sender:` if present. Verified on SMTP 465, 587 and JMAP EmailSubmission: own address, own alias
   and a **group member sending as the group** (envelope and header both the group) are accepted; a forged header
   From (local or external), a non-member using the group address, two From addresses, a forged `Sender:` and a
   missing From are refused (5.5.3; JMAP `forbiddenToSend`). Decision: members may send as the group only with the
   group as envelope sender (the identity Stalwart creates for them does this). Regression checks in
   `npm run stack:verify`. Consequence: "send on behalf" (`Sender: delegate`, `From: owner`) cannot pass this
   rule as written — Phase 4.1 adds an explicit, audited exception if we offer it.
2. **Lists accept anyone.** Members-only posting must be enforced by us (below).

## What the control plane owns vs what Stalwart enforces

| Concern                                                           | Control plane (Postgres, our services)                                                          | Stalwart                                                             |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Membership of shared mailboxes, lists, dynamic lists              | Source of truth, permission + ownership checks, audit, plan limits                              | Applied state (`memberGroupIds`, `recipients`) via provisioning jobs |
| Who may send as / on behalf / post to a list                      | Policy + check in the BFF before submission; audit                                              | Identity existence; envelope sender match                            |
| Delegation grants (full access, folder sharing)                   | Grants table, expiry, visibility to the mailbox owner, audit                                    | `shareWith` ACLs (reconciled per folder)                             |
| Mail rules                                                        | Rule model, validation, compilation, versioning, audit                                          | Executes the compiled system Sieve                                   |
| Limits (members per list, lists per account, expanded recipients) | Enforced before write; counted in sending limits                                                | Throttles as a backstop                                              |
| Reconciliation                                                    | Reconciler compares desired vs applied (groups, lists, ACLs), reports drift, never deletes mail | —                                                                    |

## List posting policy (abuse control; see `03-anti-spam-and-abuse.md`)

- Default: **members only**. Options: members only · anyone in the account · allowed senders list · anyone
  (Supporter/Plus only, off by default, needs the list owner's confirmation and a trust tier ≥ standard).
- Enforcement: a per-account system Sieve rule generated from our policy rejects non-allowed senders at DATA
  with a clear bounce; the BFF refuses webmail sends to a list the actor can't post to.
- Every message to a list counts **each expanded recipient** against the sender's sending limits.
- Caps (configurable in the private ops config, published values in `packages/shared` when shipped): members per
  list, lists per account, external members per list.

## Visibility and audit

- Every grant/revoke/membership change is a `mutation()` with an audit entry (`shared_mailbox.*`,
  `distribution_list.*`, `delegation.*`, `folder_share.*`, `send_as.*`, `send_on_behalf.*`, `mail_rule.*`,
  `resource_mailbox.*`, `message_trace.viewed`; catalogue in `packages/core/src/audit/catalogue.ts`).
- A mailbox owner always sees who has access to their mailbox and folders (Security activity page), and is
  notified when full access or send as is granted on their mailbox.
- Staff never get delegation; support uses act-as (audited, never mail content).

## Permissions (matrix: `packages/shared/src/rbac`, human view: `roles.md`)

`shared_mailbox.read|manage`, `distribution_list.read|manage`, `delegation.read`, `delegation.manage.own`,
`delegation.manage.any` (**critical**, Owner only), `forwarding.manage.own`, `forwarding.manage.any`
(**critical**, Owner only), `mail_rule.read|manage`, `message_trace.read`, `resource_mailbox.manage`.

## Provisioning order (from the probe)

Stalwart refuses to delete linked objects (`objectIsLinked`): delete list → remove members from groups →
delete group/accounts → delete `DkimSignature`s → delete domain. Provisioning jobs follow this order and
retry; the reconciler reports leftovers.
