# 04 — Data model (control plane)

Last updated: 2026-10-30 (`mailbox_delegation` added, migration 0029, ADR-0026; `data_export`, `account_deletion`, ADR-0025; `act_as_session`, ADR-0023; profile photos; names). Postgres 17. **Never mail content** (rule 24). Domain types live in `packages/core`; tables live only in `packages/adapters/src/db-postgres/schema.ts` (ADR-0008). Every migration is logged in `migration.md`.

Conventions: `uuid` primary keys (v7, time-ordered), `created_at`/`updated_at` `timestamptz`, soft delete only where noted, citext for emails, and every account-owned row carries `account_id` for scoping.

**The platform domain has no row** (ADR-0021): free addresses (`name@<PLATFORM_DOMAIN>`) are `mailbox` rows like any
other, on a domain that is configuration (`deps.platform.domain`), owned by no account and never a `customer_domain`
(customers can't add it). Per account: `PLANS.<plan>.platformMailboxes` (Free 1) or, on paid plans, within
`MAX_MAILBOXES`.

| `retired_platform_address` | address (pk, lowercase), account_id (no foreign key), retired_at | Built (migration 0015). A platform-domain address that was in use and is gone (purged mailbox, its masked aliases, a deleted masked alias): never handed to a different account; never deleted. |

**Staff suspension** (migration 0017; `packages/core/src/platform/suspension.ts`): `customer_account.status` is
`suspended` while `suspended_at` is set, with `suspension_reason` (a `SUSPENSION_REASONS` category, shown to the
customer), `suspension_note` (staff-only, never shown to the customer or emailed) and `suspended_by` (staff user id).
`user_profile` has the same four next to its `suspended` flag (the person's console sign-in). `mailbox_staff_hold`
(mailbox_id, kind `account` | `person` | `deletion`, created_at; pk both) marks each mailbox a suspension — or an
account deletion waiting out its grace period (ADR-0025) — suspended, so lifting resumes only those, and only once no
hold is left.

**Add a user** (migration 0018; `packages/core/src/mailboxes/add-user.ts`): `mailbox.display_name` (sender name, sent
to Stalwart as the account description) and `mailbox.must_change_password` (webmail first-sign-in step);
`user_profile.must_change_password` (console gate) and the optional profile details `job_title`, `department`,
`office`, `office_phone`, `mobile_phone`, `street_address`, `city`, `region`, `postal_code`, `country` (ISO 3166-1
alpha-2 from `packages/shared/src/profile.ts`). Profile details are personal data: never logged, audited only by field
name, and removed with the person (`user_profile` cascades from `auth_user`).

Member profile fields used by signature placeholders (`display_name`, `job_title`, `phone`) live on
`account_membership` (per account, editable by the member and by User Admins).

**Profile photos** (migration 0021; ADR-0022; `packages/core/src/avatars`): `avatar` — id, user_id (→ `auth_user`,
unique) **or** mailbox_id (→ `mailbox`, unique; only for a mailbox without a person), content_type (`image/webp`),
data (`bytea`, a 256-pixel square we re-encoded, no metadata), byte_size (≤ 256 KiB), sha256 (its first 16 hex
characters are the version in the photo's URL), updated_at. Exactly one owner per row (`CHECK`); removed with the
person or the mailbox (`ON DELETE CASCADE`). A mailbox with a person shows the person's photo. `auth_user.image`
(better-auth's column) stays unused: we never store a remote URL.

**Names (one source each, rule 61).** A person has one **name**: `auth_user.name` (with `first_name`/`last_name`), shown
in the console app bar, person menu, Profile and People pages and to staff; set at sign-up, invite or "Add a user". Mail
carries a different value on purpose, the **sender name** — what recipients see in "From", chosen per address: the mail
server's JMAP identity name for each address a mailbox sends from, edited in webmail Settings → Account ("Sender name,
as people see it on your mail") and stored only on the mail server. `mailbox.display_name` is the name an admin gives
the mailbox in the console (Mailboxes → Display name, "Add a user"), sent to the mail server as the account's
description. Whether the mail server names a new identity after that description hasn't been verified against the pinned
server (identities observed without one are named after their address), and editing either never updates the other: an
open rule 61 item in `handoff.md`. The console Profile page and the webmail say which is which.

## Scoping rule

Every repository method that reads account-owned data takes an `accountId` (or an actor that resolves to one) and filters by it. There is no "find by id" without scope. Cross-account reads return "not found", which surfaces as 404 (rule 25). The contract test suite checks this for every adapter.
